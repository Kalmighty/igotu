## Implemented application changes

- `backend-access.js` provides version compatibility checks and purpose-specific API calls; `profile-guard.js` fails closed when the coordinated backend is unavailable; every Client, Provider and Admin initializer awaits it. Version metadata is not an authorization credential; RLS/RPC guards independently enforce actual database identity/role/status/history.
- Recommendations use a request-specific server response for category/specialization, availability, distance, ratings, completions and decline exclusions; no cross-user profile/booking fanout in the browser.
- Provider dashboard/incoming/assignment/messages/report pages use assigned-request projections. Client details and both messaging pages use minimal request-derived peers. Email/phone contact disclosure is removed; Messages remains available. Message loads/read flags are restricted to the current pair, protecting the UI from former-assignment thread mixing.
- Shared `payment-receipts.js` resolves server-authorized paths and signs five-minute previews, with fresh signing on open and explicit failures/empty states. Client uploads persist paths without public URLs. Client/Provider/Admin payment views share this behavior; cash/transfer workflow stays offline.
- Request creation retains a session-scoped idempotency key across transport retries and clears it only after confirmed creation. Existing image-failure retry/edit behavior is preserved. Provider profile uses a single transactional API for profile/skills/specs/hours/basic details.
- A local staging artifact builder validates the staging reference/publishable key and preserves source/output directories without contacting any environment. Browser notification emission and the helper are removed from all actions; the coordinated server cutover owns events. A failed backend action never becomes fake frontend success.
- Admin verification page adds a read-only, keyset-paginated legacy inconsistency queue linking to normal review history. Existing approve/reject/resubmit workflow remains the sole decision path.

[Rollout and existing-user decisions](rollout.md) describe the four ordered review-only drafts, notification/storage handoff, operator gates and recovery. The historical impact numbers—**7 active Clients, 35 Providers, 28 inconsistent Providers**—are user-reported prior findings, not counts queried in this phase. No account was approved, edited or deleted. New verification may interrupt legacy users' existing assignments; a transition and communication policy needs approval.
