## Findings and design

The reported public bucket bypasses Storage SELECT policies for public downloads. Saved D04 also treats request images as generic workspace content; a private bucket alone does not establish the required owner/confirmed-Provider boundary. Existing D02 masks the Provider URL before confirmation, but masking a field cannot revoke a previously known public URL. Existing D03 requires a canonical public URL in `client_save_request_image(text,text,text)`.

The candidate uses **authenticated Storage downloads**, not signed bearer URLs. The browser first calls the authenticated `request_image_reference(request_id)` API, which resolves an image path only for an authorized request. Storage independently checks the same ownership/role/status boundary on the actual download. Its restrictive SELECT policy also requires the documented `storage.allow_only_operation('object.get_authenticated')` operation: listing, signing and non-download reads are denied even for otherwise authorized browser readers. No caller-supplied image URL or browser-side path extraction authorizes access. No secret/service-role key is used.

| Caller | Authorized image reads |
|---|---|
| Active, verified/profile-complete owning Client | Own request image, including pending/completed/cancelled requests |
| Active, verified/profile-complete selected Provider | Only `confirmed`, `in_progress` and `completed` requests still assigned to that Provider |
| Active authorized Admin | Associated request images, preserving the existing Admin workspace rules |
| Anonymous, unrelated Client, nonselected Provider, awaiting-confirmation Provider, suspended/unapproved account | Denied |

Private security-definer helpers are in the existing unexposed private schema, with empty search paths, explicit subject/workspace checks and narrow EXECUTE grants. New public reader/capability wrappers are security invoker. The existing save-RPC signature/security mode is preserved and gated by a reviewed live definition fingerprint. Restrictive SELECT/INSERT/UPDATE/DELETE policies apply only to `request-images`; narrow positive policies allow authorized reads and new owner-folder Client uploads. Existing policies and unrelated buckets are not dropped or weakened. Browser overwrite/upsert/delete is denied for this bucket so an image cannot be swapped under a previously approved association. Privileged service-role writers remain outside the browser RLS boundary and must be paused/audited separately.

The UI downloads on **View request image**, displays a browser-local Blob preview, and revokes it after two minutes, on auth-state changes/page exit, or when its card disappears. Each reopening rechecks the reference and download; failures never fall back to a stored URL. MIME and size are restricted to JPEG/PNG/WebP at 5 MiB. The preview is responsive and includes an Open image link. The two-minute timer is a browser display lease, not a server-side JWT expiry/revocation promise. A recipient can retain pixels already downloaded, save an image or keep an already loaded tab; no signed URL or Blob scheme can recall those bytes. Browser timer suspension can delay expiry. This design avoids minting shareable HTTP bearer URLs with caller-chosen lifetimes or signed-URL CDN caching behavior.

## Existing files, URLs and SR0052

- No bulk UPDATE of service requests, URL/path backfill, file copy/move/delete, Storage reset or re-upload is included.
- The server resolves a missing path only from the exact staging canonical public URL prefix. A stored path must agree with any stored legacy URL, belong to the request Client's folder, and resolve to an object owned by that Client. URL queries, foreign hosts, encoded/traversal paths and conflicting associations fail closed.
- Existing image records, including URL-only records, remain byte-for-byte unchanged by the proposal. The save RPC accepts a matching canonical URL from an old caller for upload compatibility, but **new association writes store a path and NULL URL**. New callers send NULL URL and upload with `cacheControl: "0"`, `upsert:false`.
- Image association changes require an owned pending request, matching the existing edit UI. A Storage object row lock serializes reuse checks. Multiple-request path reuse, missing objects, unknown ownership, unsupported legacy MIME/size, or conflicting URLs block installation; do not auto-repair them.
- SR0001, SR0002, SR0011 and SR0052 are not test targets. Existing versioned evidence/procedures are unchanged. Later live verification of SR0052 must be separately authorized and read-only: hash the request row/association/object metadata, verify authorized retrieval without altering application state, then compare the hashes. Do not replay uploads, confirmation, payment, review or messaging for these records.
- Old public URL strings remain historical metadata, not UI sources. The frontend never extracts/fetches those URLs. The private bucket must reject them after the separately approved cutover and observed cache transition.

## Safe rollback

- Before SQL commit, any error rolls back the entire proposal. That leaves the previously public bucket's known risk unchanged; it does not establish privacy. Stop and report it.
- After a successful cutover, keep the bucket private and restrictive boundaries in place. If UI/compatibility fails, pause image operations and roll the frontend back or show image-unavailable controls while retaining private Storage. Other workflows can continue without new images if separately approved. Older public-URL rendering may show unavailable images against the private bucket; that is a safe failure.
- Do not automatically restore public visibility, broad reads, overwrite/delete permissions, or old URL requirements. Restoring backend definitions/policies requires separately reviewed captured definitions/ACLs and explicit authorization. Prefer a reviewed forward correction. Preserve all files, paths and association rows and compare protected hashes before resumption.
- Previously minted signed URLs can remain valid independently of new signing restrictions; review signing audit evidence and supported Supabase revocation/expiry options before claiming complete cutover. Auth key rotation does not revoke Storage signing keys. Any project-wide Storage signing-key intervention needs separate approval and cross-feature review. Already downloaded/publicly cached copies cannot be recalled by this change. Do not promise otherwise or treat logout/Auth key rotation as revocation of previously downloaded content.
