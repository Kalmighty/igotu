## C. Catalog compatibility and dependencies

The saved catalog matches the core 14-table model, the existing payment-per-request and review-per-author/request uniqueness, Provider skill/spec/hour keys, participant foreign keys, ID triggers, enum types and the legacy RPC parameter names/types. The 13 replaced public RPC signatures and normalized return types are preserved. `admin_update_user_status` correctly uses **`public.account_status`**, not `user_status`, in D03. The quarantined empty baseline intentionally preserves the old function body only so the D01/D03 fingerprint gate can verify the starting point before replacing it.

The snapshot-compatible empty baseline is executed explicitly first even though its newly generated timestamp is later than the four existing filenames; never infer order by globbing timestamps. The ordered [migration manifest](migration-order.json) records this.

The saved catalog lacks the two consent columns, request creation/event keys, unique pending-verification index, secured reader APIs, atomic profile RPC, private namespace, new policies/triggers and compatibility endpoint. D01–D04 introduce those in dependency order. Existing indexes/constraint definitions are compared offline; the saved latest-verification index and new references/indexes support the proposed lookups, but no EXPLAIN/latency result is claimed.

The reader shapes intentionally expose assigned requests, request-derived peers and recommendation aggregates rather than raw foreign profiles/booking rows. No exact pre-confirmation structured Client location, description or image URL is returned by the Provider projection. Recommendations retain specialization/skills, availability, weekly hours, distance, full ratings/completions and decline/busy exclusions. Exact date/time conflicts remain the existing booking model; no duration or marketplace/application workflow is introduced.

Every function body, policy, grant, trigger, phase transition and dependency was reviewed against the saved metadata and frontend call inventory. Offline checks parse SQL/PLpgSQL and check creation order and replacement contracts. They **cannot** plan PostgreSQL row/composite expressions, establish RLS behavior, prove lock snapshots or verify Supabase API configuration. [The execution guide](guide.md) describes the missing evidence and recovery for each stage.

## D. Security and identity readiness

- Registered role/status/approval comes from trusted database rows and review history. URL/UI/localStorage/user metadata never grant privileged access. The preserved signup bridge normalizes user-editable signup role to Client/Provider only; Admin provisioning is an explicitly authorized operator fixture step.
- Not submitted/pending/rejected users have own account and verification access, not normal workspaces. Approved incomplete accounts may read/save their own onboarding data; normal workspaces open after profile completion. Suspended accounts remain denied, even with valid approval history. Admin does not self-register or bypass active status.
- New verification requires recorded true consents, valid owned private documents, role consistency and a single pending request. Only the latest pending request can be approved/rejected through the active Admin RPC. Old consent is never fabricated. Last-four identification storage is preserved; no full ID number or real document was accessed.
- Definer helpers have explicit search paths/owners, wrappers have narrow APIs and effective EXECUTE is checked. Installation metadata additionally has RLS and no browser grants. Private schema must be excluded from effective REST/GraphQL exposure: a NULL SQL setting is **not** evidence. Explicit exposure in an available SQL setting now stops installation, while dashboard/config review and both negative header probes remain mandatory.
- Message and payment/review writes validate actual current service participants/state and preserve uniqueness; role labels are never credentials. Historical messages remain visible to their actual sender/receiver, while the UI displays only the current pair. Do not reinterpret another Provider's messages as the current conversation.
- Identity/payment/report buckets are private; receipts use owned references and short signed previews. Report/identity metadata deletion is serialized against references. Cached/downloaded/public historical proofs and issued signed URLs still need retention/remediation decisions. `request-images` remains an existing public design and free text may disclose location/contact data; a private-image/content policy remains a production blocker.
- Database status/approval checks do not, by themselves, invalidate a stolen unexpired JWT after ordinary Auth sign-out. Browser cleanup/cross-tab behavior is tested locally; **immediate server JWT revocation is not proven or newly implemented**. Confirm the required revocation guarantee, actual Auth expiry/session behavior and any server-side session check in staging before accepting DB-08. Do not label a still-valid JWT test as a passed denial.
- External notification/privileged writers must be inventoried and paused. Event-key uniqueness and transactional source triggers preserve intended recipients and retries, but every notification source and rollback path still needs real staging evidence.

## E. Existing users and history

Do not treat the historical 7/35/28 counts as a current reconciliation queue. Consistent prior approved history remains valid under the recorded contract, while legacy flag-only accounts remain blocked. Suspension is not a verification-history defect. The queue does not approve or rewrite anything.

Their request/assignment/payment/review history remains stored. Completed work is not deleted or reassigned. Any exceptional approval, historic data repair, support access or assignment transition needs separate policy and authorization. Incomplete legacy profiles now require completion before business access; existing own approved Provider onboarding data remains readable so the form does not silently wipe it.
