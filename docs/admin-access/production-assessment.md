## Dependency order and deployment boundaries

After a complete proposal and separate approval, use a bounded maintenance window and verify actual writer pause/drain. Conceptual order is foundation → private readers → integrity writers → coordinated ACL/RLS/Storage/notifications cutover → compatibility sentinel last. Each step needs a validated predecessor, actual catalog/fingerprint checks and explicit stop-on-error. If stages are already installed, design incremental changes; never rerun the original fresh-install scripts. A phase number alone is not a security acceptance result.

Before releasing application traffic, validate in isolated synthetic testing with all approved states and actors: Admin, owning/other Client, selected/nonselected Provider before/after confirmation, inactive, unverified/pending/rejected/inconsistent accounts and anonymous. Prove own-user and authorized positive controls first; missing RPC/401/500/network errors cannot count as expected denials. Test private-schema rejection, actual RLS and function grants, signup/verification/approval, complete service/payment/review/report/messaging flow, signed files, duplicate/idempotency/concurrency and atomic rollback, notification counts and actor revocation behavior. UI fixture tests cannot satisfy these checks.

Deploy only the frontend release whose dependencies match that verified backend, and only under separate deployment approval. Keep maintenance/error behavior for incompatible clients; do not leave older clients writing through a partial notification or RPC cutover. Require an explicit resumption authority and post-release monitoring/stop criteria. This patch is not automatically deployed with a backend change.

## Stop and rollback limits

Stop for unapproved target/operator/time window, unknown schema/grant/routine drift, changed fingerprints, mismatched predecessor, record/owner/path inconsistency, unsafe API exposure, ambiguous commit result, unknown cache behavior, unsupported Storage operations, failed positive controls or any unexpected error. Preserve evidence; do not auto-repair, drop objects, change hashes/allowlists, weaken policies or retry SQL blindly.

Each transaction can roll back its own uncommitted work; later failure does not undo earlier commits, emitted notifications/emails or object/cache changes. After an ambiguous disconnect, inspect actual installation/catalog under approval before deciding any next action. Keep writers paused. Do not restore permissive legacy grants, make private buckets public, reintroduce public URLs or roll back the frontend to regain broad access. Forward repair, restoring a verified compatible snapshot, and resource/data restoration require their own reviewed plan and approval. Previously downloaded media cannot be recalled; sequence gaps are not a repair target.

**Decision required later:** approve the bounded evidence collection first. Production execution approval can only follow a concrete production-specific migration/backup/validation/rollback packet; this assessment does not supply or request that execution approval.
